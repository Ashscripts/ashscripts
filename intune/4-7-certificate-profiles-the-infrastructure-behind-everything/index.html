The Scene

Tuesday morning. Ashpak is running a full connectivity test on a freshly enrolled Windows laptop. He opens the corporate Wi-Fi. Error. He tries the VPN. Error. He opens Outlook. Certificate error. He sits back. Every profile he's built over the last week; Wi-Fi (EAP-TLS), VPN (certificate auth), email (S/MIME); references a certificate. A certificate that hasn't been deployed yet. The profiles are there. The settings are right. But without the underlying certificate infrastructure, none of it works. He pulls up his notes from the planning phase. There it is, circled in red: He should have built this lesson first. But in the real world, this happens. Teams deploy profiles, then wonder why nothing works; and trace it back to missing certificates. Today, Ashpak builds the certificate infrastructure that underpins the entire AshScript device management stack.

CERTIFICATE INFRASTRUCTURE COMPONENTS
COMPONENT 1: Certificate Authority (CA)
The trusted issuer of certificates
AshScript uses: Microsoft AD CS (on-premises)
OR: Cloud-based CA (DigiCert, GlobalSign via Intune)
COMPONENT 2: NDES / Intune Certificate Connector
The bridge between Intune and the CA
Intune asks NDES: "Issue cert for this device"
NDES asks CA: "Issue this cert"
CA issues cert
→
NDES returns to Intune
Intune delivers to device
COMPONENT 3: Certificate Profiles in Intune
Two types:
• Trusted Certificate Profile (Root CA cert)
• SCEP/PKCS Certificate Profile (device cert)
AshScript's choice: SCEP for device certificates (Wi-Fi, VPN authentication) because the

private key never leaves the device. PKCS for user certificates (S/MIME email signing) because the certificate needs to follow the user across devices.

How SCEP Certificate Issuance Works

This is the complete flow when a device receives a SCEP profile:

Step 4: SCEP Profiles for All Platforms

SCEP CERTIFICATE ISSUANCE FLOW
1. Intune pushes SCEP profile to device
▼
2. Device generates key pair
Private key → stored in TPM (never leaves)
Public key → used to create CSR
▼
3. Device creates Certificate Signing Request (CSR)
CSR contains public key + subject info
▼
4. Device sends CSR to NDES server
URL https://ashscript-ndes01.ashscript.com/ ...
▼
5. NDES validates request with Intune
"Is this a legitimate Intune device?"
Intune "Yes; device ID matches"
▼
6. NDES forwards CSR to Certificate Authority
▼
7. CA issues certificate
Signs with AshScript Root CA
▼
8. Certificate returns CA → NDES → Intune → Device
▼
9. Device installs certificate in certificate store
Certificate profile Succeeded
▼
10. Wi-Fi/VPN profiles can now use this certificate
for authentication

Concept Remember This

Deploy order Root CA first → SCEP/PKCS second → dependent profiles third SCEP Private key on device; never transmitted; most secure PKCS Private key generated by CA; simpler but key travels Certificate Connector Bridge between Intune and on-premises CA; must stay healthy TPM-backed key Private key in TPM hardware; cannot be extracted Renewal threshold 20% = auto-renews 73 days before expiry for 1-year cert

Certificate revocation Retire device in Intune → auto-revokes cert → RADIUS blocks CRL propagation Up to 24 hours; revocation not instant at authentication point NDES reachability Port 443 from devices to NDES; firewall must allow Root CA expiry Most critical event; ALL certs invalid if missed
